# Authenticated QUIC probe

Implemented: actual UDP-backed QUIC endpoints using protected identities, mutual TLS 1.3, explicit peer trust, host control permission/approval, negotiated application protocol, a new session epoch, and key-transition datagrams applied through a recording injector. No keyboard capture or OS injection is connected to this command.

## One-command local check

```powershell
.\target\debug\bricks-host.exe probe-selftest 100
```

Runs 100 synthetic press/release pairs (200 transitions). It creates two identities inside a randomly named owned temporary directory, protects their keys with current-user DPAPI, trusts their public certificates inside the test process, and binds the host to an ephemeral IPv4 loopback port. Temporary files are removed on normal completion. It does not create or replace the normal `os-store:bricks-host`/`bricks-client` identities. A process crash can leave encrypted test files in the temporary directory.

Run under your normal Windows account so DPAPI can use its profile. No administrator rights are needed. Automatic local test trust is limited to identities generated by this self-test; real peers still require the independent fingerprint verification below.

## Two-PC recording-only check

1. Build/transfer compatible Windows development binaries to both PCs. Initialize the host and client identities using [identity commands](identity-and-ownership.md). Exchange public DER certificates and independently verify fingerprints before importing trust. The host grants the client `--allow-control`; the client trusts the host without reverse control permission.
2. Copy the example configuration files. Set host `transport.listen` to its actual LAN or tunnel IP and port (for example, `192.168.1.20:47990`). Set client `transport.peer` to that reachable endpoint. The examples' default `127.0.0.1` addresses work only on the same PC. Use the configured `os-store:` identities on their respective PCs.
3. Start the host with the **client** certificate fingerprint, replacing the placeholders:

```powershell
.\target\debug\bricks-host.exe probe-host docs/examples/host.toml CLIENT_SHA256 --approve-control
```

4. Within 30 seconds, start the client with the **host** certificate fingerprint:

```powershell
.\target\debug\bricks-client.exe probe-client docs/examples/client.toml HOST_SHA256 100
```

The host handles one connection and exits with an aggregate report. The client prints timing/counter data plus the resolved application configuration and its hash. A rejected client also ends that one-shot host invocation. If Windows firewall blocks the connection, use an appropriately scoped private-network/application rule; this command does not change firewall settings or configure a router. LAN and existing IP tunnels use the same endpoint code. No custom NAT traversal, discovery, or relay is implemented.

These commands cannot remotely type, move a cursor, or control an application. The explicit host approval flag exercises the admission policy before enabling any future OS backend.

## What the measurement means

For each synthetic transition the client timestamps immediately before `send_datagram` and waits for a matching application ACK on the reliable control stream. The host sends this ACK only after the recording state machine accepts the transition. The measured interval includes transport queueing, both network directions, receiver processing, and the control-stream ACK path. It is **not** capture-to-submit, one-way network latency, input-to-photon, or a fair QUIC-versus-UDP bake-off.

Loopback reports use `loopback_quic_synthetic`. Other endpoint addresses use `two_endpoint_quic_synthetic`; an address alone cannot prove two physical PCs or distinguish LAN/tunnel/relay. Record the actual machines, route, load, build, and conditions separately. This is an uncalibrated debug diagnostic, not an acceptance benchmark, and no samples are silently excluded as warm-up.

Pairs range from 1 to 5,000. This first probe is stop-and-wait: it sends each datagram once, then waits for its ACK. There is no application retransmission, NACK, reorder buffer, snapshot recovery, or high-rate mouse stream yet. QUIC protects and congestion-controls datagrams but does not make them reliable. A loss, gap, wrong epoch, malformed message, or timeout ends the run; missing work is not relabeled as successful delivery.

## Lifecycle and bounds

- TLS validation and control approval precede epoch grant; early-data input is disabled.
- One bidirectional control stream, no unidirectional streams; bounded transport buffers and 4 KiB final client-summary cap.
- Host validates the exact current peer certificate before granting the shared store's exclusive control lease.
- Datagram size is bounded by the host configuration and the 48-byte experimental transition codec; no native memory-layout casting.
- At most 10,000 received datagrams and 60 seconds of event-loop runtime per session.
- The CLI uses the configured input-silence timeout (250 ms in the examples). The local self-test allows 2 seconds for exploratory runs. Tests use explicit diagnostic timeout values rather than asserting gaming deadlines.
- A 20 ms control tick refreshes persisted trust through a blocking worker and checks the lease even while input is idle. Blocking refresh/ACK writes have timeouts. This single diagnostic actor is not the future dedicated input-thread architecture and has no hard real-time timing guarantee.
- Disconnect, silence, malformed/stale data, revocation, and normal stop all release recorded owned state. The guard also attempts cleanup on drop. There is no OS-held key in this probe; actual OS release and process-crash watchdog behavior remain separate acceptance work.

## Verification

Real loopback tests exercise successful mutual authentication/data application, missing control permission/approval, an untrusted client, and recorded-key release after disconnect, malformed datagrams, an old epoch, idle revocation, and silence. They do not inject OS input. The initial compiled self-test result is recorded in [QUIC loopback evidence](test-results/2026-10-23-quic-loopback.md).

Next: record the two-PC probe result, then connect a bounded capture queue and explicit OS backend with proper per-event timestamps and application recovery. Do not treat successful synthetic loopback as completion of M2's real input path or its LAN latency gates.

If a second PC is unavailable, the separate [single-PC recovery check](recovery-selftest.md) exercises the transport-independent key-recovery engine offline. It requires no identity/network setup and leaves this probe's no-retry semantics unchanged.
