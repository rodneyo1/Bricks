# Agent, network recovery and single-PC performance work

Implemented scope: a separate per-user Rust agent, a local control SDK used by Slint, real QUIC critical-key recovery, fault/lifecycle tests, and a sustained recording-only benchmark runner. Live Windows input forwarding, mouse transport, code pairing, discovery, media and external OS cleanup supervision remain gated. This work does not establish a two-PC or physical gaming result.

See the [completed 2026-10-23 report](test-results/2026-10-23-agent-recovery.md) for both recovery profiles, measured timings, resource budgets and pending gates.

The [2026-10-24 performance report](test-results/2026-10-24-performance-fixes.md) records the corrected strict 30 ms profile: 35/35 network cases and 1.3 million transitions, under the declared Games scheduling/timer policy. It also preserves worse observed latency tails, unresolved active CPU and complete-package size budgets. No target was relaxed.

Receiver gap ages are tracked by bounded, increasing produced-history ranges. Once an old range is fully applied, it no longer ages newer missing history. Partial progress within an old range, duplicates and repeated heartbeats cannot renew that range's deadline. The healthy in-order path does not enqueue these ranges. This corrects premature 30 ms stops without increasing the cutoff or postponing healthy input.

## Product runtime

`bricks-agent` owns `bricks-control::Controller`, saved PCs, settings, protected identity setup and diagnostic/report state. `bricks-ui` owns presentation only. Starting Bricks connects to the existing user/session agent or starts the bundled `bricks-agent.exe` without a console window. Closing the UI closes its SDK connection; UI-owned recording operations are cancelled. The auto-started agent exits after 30 seconds without a client or active operation. Explicit headless launch can stay running without a UI:

```powershell
.\target\release\bricks-agent.exe
```

Ctrl+C requests shutdown. No remote listener, OS capture, input injection or background sharing starts with the agent. Normal stop waits for operations; an unexpected process exit leaves an unclean marker. A restarted agent reports `unknown_local`, a fresh instance ID and reconciled saved state. It does not use empty process memory to assert that Windows keys were released. Live input capability remains false.

The UI shows unavailable/reconnecting feedback when the agent connection breaks, disables mutations while unavailable, reconnects and refreshes state, and never automatically replays an uncertain mutation. A new agent instance clears the frontend's cached report availability. Settings > Advanced adds **Check network recovery** and **Cancel check**. A cancellation request is displayed separately from confirmed cancellation; a partial cancelled run does not replace the last completed report.

The portable bundle contains the Slint executable plus an optimized agent and notices. Keep the folder together. The UI does not carry input packets, GPU frames or per-key JSON. The agent's storage thread and IPC tasks are separate from the network-recovery worker.

## IPC implementation and bounds

- A Windows named pipe is scoped by the current SID, Windows session and canonical data-directory hash. The DACL grants the current user; remote clients are rejected. Both ends query the connected peer process and compare its token user and session. Pipe-name obscurity is not authentication. The threat boundary is the Windows account/session, not protection against another program already running as that same account.
- Four admitted clients and one bounded pending pipe instance are permitted. Each connection admits one active operation, with a 16-frame bounded request queue; the service admits at most 16 queued/active operations. This is deliberately tighter than the design's 16 outstanding requests per client. State subscribers have 128 entries; overflow disconnects them instead of hiding lost updates.
- API version 1 uses a 4-byte little-endian length plus typed UTF-8 JSON, with a 64 KiB payload limit. Unknown/malformed messages and incompatible handshakes are rejected. Partial headers/bodies have deadlines after their first byte. Dedicated readers preserve framing when cancellation/events arrive; cancelling an incomplete read and resuming midway through a frame is avoided.
- Snapshot creation and subscription registration share the state lock. Messages carry agent instance and sequence. State events contain complete snapshots; the SDK requests refresh on a detected gap and discards superseded sequence values. Reconnection replaces state from a new handshake. This is not a replay log of input events.
- `Accepted(operation)` is admission, not completion. Completion carries the confirmed result and snapshot. Cancel checks ownership, is idempotent after a terminal operation, and cannot cancel another connection's operation. Storage writes already committed are not undone. Snapshot/cancel/stop requests do not queue behind the diagnostic storage worker.

Implemented commands are device save/edit/forget, settings, identity setup, diagnostic run/export, snapshot, cancellation and idempotent stop of owned recording operations. The broader pairing/sharing/live-session command groups in the [target SDK contract](control-sdk.md) remain unavailable. Direct cross-account/cross-session interactive negative tests still need suitable accounts/sessions; current checks cover real permitted pipes and the enforced token/session policy, not a completed security audit.

## Recovery transport and performance decisions

`bricks-transport::reliable` shares authenticated QUIC admission with the existing probe: pinned identities, host approval, control permission, exclusive ownership and fresh random epochs. It wraps the bounded core recovery receiver and checks the in-memory authorization lease before delivery and while idle. The sender retains exact transitions and original timestamps until cumulative application ACKs; idle retries recover a lost final release. Versioned 28-byte ACKs include epoch and applied-through ID. Old-epoch input never refreshes liveness or reaches the injector.

The actual encrypted-loopback harness streams transitions rather than waiting for an ACK after each one. Healthy arrivals apply immediately. There is no synthetic hold scheduler or mandatory jitter buffer. Only cumulative feedback is batched: by default every eight applied transitions, with a 5 ms maximum pending feedback delay; duplicates/gaps prompt feedback. These settings are typed, bounded lab options and included in each result. QUIC ACK-frequency negotiation requests matching bounded transport feedback, allowing feedback to share packets. Changing these settings does not delay input application. They are not yet a negotiated production application wire policy.

Retries account for the feedback wait, measured handshake RTT and a scheduling margin, within the existing 2-20 ms limits and at most one third of the selected history cutoff. The 30 ms cutoff is unchanged. Authenticated grants communicate the actual retry/cutoff values. Setup is timed separately from steady traffic. A persistent generator timer and a current-thread runtime avoid repeated timer registration and an extra network worker. Resource queries run on a separate monitor thread, whose CPU still counts in the combined process measurement.

Maintenance now uses the next ACK, retry, impaired-link delivery or receiver watchdog deadline, without a fixed 1 ms polling wake. Core deadline accessors preserve existing fail-closed expiration and lost-final-release behavior. The optional `games_scheduling` lab setting registers only its current thread with the [Windows MMCSS Games task](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service). Its non-Send guard [reverts registration on that same thread](https://learn.microsoft.com/en-us/windows/win32/api/avrt/nf-avrt-avrevertmmthreadcharacteristics). This is a measured scheduling experiment, not a real-time guarantee or a permanent system change. `tools/run-single-pc-bench.ps1 -GamesScheduling` selects it explicitly.

The client receives its fresh epoch and bounded recovery policy in a versioned 32-byte grant over an authenticated reliable QUIC control stream. Input and cumulative ACKs then use datagrams. Authenticated 28-byte idle heartbeats carry epoch and highest produced ID, preserving a ten-second held key without injecting repeats. A heartbeat advertising missing history starts/preserves the gap deadline; trickling partial history cannot renew that deadline. Old-epoch heartbeats do not refresh liveness.

Send history is preallocated. The bounded owned-key set uses a preallocated sorted vector rather than allocating a tree node on each press. Receive reordering allocates only on the impaired path. Packet ownership inside Quinn and instrumented report buffers still allocate; zero-allocation transport is not claimed. The laboratory actor and QUIC driver share one current-thread Tokio runtime. Storage, trust-file reads, UI rendering and JSON formatting are outside the receive/apply path. The future runtime must also drive out-of-process trust refresh on a separate control worker before OS input is enabled.

Windows active lab work requests 1 ms timer resolution and releases the request on every normal/error/cancellation exit. Idle agents do not make this request. It is a request, not a guarantee, and changes neither QPC accuracy nor physical input timing. Windows 11 visibility/power policies and scheduling still affect waits. These limits follow Microsoft's [timeBeginPeriod documentation](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod). A high-resolution waitable-timer backend remains an option if measured scheduling tails justify its cost; [Microsoft documents its platform requirements](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw).

Recovery uses the validated engine policy: bounded 256-entry send history, 64-entry reorder window, 2–20 ms retry limits, 30–150 ms history recovery limits, and 250 ms silence timeout. The initial lab starts from a declared 1 ms RTT reference and selects the 30 ms minimum. Sustained tests exposed false session aborts after Windows scheduling/feedback stalls, so the runner also supports an explicitly labelled 150 ms cutoff within those existing bounds. The runner defaults to that conservative experiment; `-StrictRecovery` selects the original 30 ms experiment. Each new report records its selected cutoff, separately from latency. This is not a delay added before healthy input application or a relaxation of the latency targets. Live RTT adaptation remains pending. Large jitter/outages can still stop an epoch; lost and ungenerated history remain counted, and cleanup never counts as delivery.

## Test and benchmark procedure

```powershell
powershell -ExecutionPolicy Bypass -File tools/run-single-pc-bench.ps1
```

The runner builds optimized binaries, preserves the exact executable hashes, captures OS/CPU/GPU/power metadata where available, and writes a fresh `artifacts/single-pc-*` directory. `-SkipBuild` uses already-built optimized artifacts; `-Quick` is a development screen with smaller counts, not acceptance evidence.

The full run includes prior warm-up traffic, five healthy 10,000-transition blocks, five 20,000-transition seeded blocks for each 0.5/1/2% bidirectional application loss, 60 seconds each at nominal 1/4/8 kHz, duplication/reordering at 0.1/1%, delay variation at 1/5/10 ms, packet bursts of 2/5/10, and a lost final release. It also runs fourteen real-QUIC lifecycle cases including a ten-second held key, actual agent process crash/restart/reconciliation/cancellation checks, and 60 seconds of idle-agent CPU/private-memory sampling. A fault-stopped case is not a completed 60-second run; preserve it and label any follow-up profile separately. High-rate critical-key transitions stress transport/state; they do not pass the mouse-motion gate.

Impairment occurs before encrypted QUIC datagram send, independently in both directions. It exercises application recovery but does not reproduce NIC congestion, router queues, physical asymmetry, tunnel encapsulation or QUIC packet loss below encryption. Real bridge/router impairment remains required. Warm-up uses prior traffic on a separate connection; hardware protocol-compliant per-condition warm-up, randomized A/B tests and controlled background load remain pending.

Every case reports scheduled options, actually generated/applied/acknowledged counts, missing and ungenerated history, recovery-deadline deliveries, retries/duplicates, fidelity errors, cleanup failures, bounded queue peaks, same-clock generation-to-recording-submit timings, pacing lateness, local handler timings, process CPU/private memory and an IPv4 bandwidth estimate. Memory samples include diagnostic buffers; CPU is the combined process running both endpoints and harness, normalized to one logical core. It cannot prove either individual endpoint's CPU budget. CPU accounting granularity makes short-run readings unsuitable for idle/active acceptance.

Schema 2 additionally records effective retry time, setup time, UDP datagram counts, maintenance wakes and actor gaps, including a pause inside a terminal handler. Its configuration fingerprint covers application config, lab options and effective retry/deadline policy; schema 1's fingerprint covered the application config only. A gap over one second marks a case `INTERRUPTED`. The analyzer separately identifies older cases whose elapsed time exceeded the entire budget, preserves their original status and never treats them as complete acceptance runs. Missing lifecycle/idle files remain missing evidence, rather than a pass for an interrupted suite.

The CLI lab makes a scoped system-required idle-sleep request and restores it on exit/error. It never overrides closing the lid or deliberately choosing Sleep; keep the laptop open and on AC during a sustained run. The October 23 overnight run has matching Modern Standby events in its preserved power-event metadata and is incomplete. Idle agents make no such request. `-HighQoS` is an explicit, separately recorded benchmark experiment; it is not selected by default and the short comparison did not establish an improvement.

Timing vectors are bounded by configured experiment length, not retained in the agent's event history. Report nanosecond units do not imply nanosecond accuracy. Handler percentiles cannot simply be added into a combined-overhead percentile, and these handler subsets omit actual OS capture/injection. Bandwidth uses QUIC UDP counters plus IPv4/UDP header estimates, includes handshake traffic, and excludes Ethernet/tunnels. It is not packet-capture evidence.

Use the [targets](targets-and-benchmarks.md) unchanged: zero healthy missing/duplicate/out-of-order critical applications; empirical deadline delivery goal of 99.99% under <=1% loss; recorded silence cleanup within 250+50 ms; 1 kHz sustained work; characterize 4/8 kHz; then the CPU, memory, size and bandwidth budgets. Keep preliminary or failing runs. Do not change a target because a run misses it. Actual C0-to-I0, paired hold error, real OS-neutral cleanup, per-endpoint loaded resources, two-PC LAN/tunnels and Sunshine/Moonlight physical comparisons remain separate gates.

## Verification limits

Real-pipe tests cover two-client snapshots, stale revisions, cancellation ownership, event overflow/reconciliation, partial frames and version/size rejection. GUI smoke covers actual agent-backed persistence and confirmed cancellation; Windows accessibility tests exercise real named fields/buttons. The crash test terminates only its own newly created recording-only agent process and verifies new instance, persistent state and `unknown_local` afterward.

Network lifecycle tests cover disconnect, silence, revocation, old epochs, new authenticated connections, competing owners, host-task abort, cleanup failure/retry, approval/permission denial, and 50/250/1,000 ms outages. An external trace retained by the test observes recorded releases after task abort. Killing an OS-injecting process is **not** covered by this: an independently verified Windows release supervisor remains an M3 requirement before enabling that capability.
